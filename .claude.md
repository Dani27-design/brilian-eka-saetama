# .claude.md — WEBSITE_APP_PROJECT_RULES

> **Purpose:** System prompt / project rules for Claude Code. Place this file in the project root. Claude **must** read this file and `CODEBASE_COMPREHENSIVE_ANALYSIS.md` before performing any work.

---

## ⚠️ Top-level requirement

- **Do not begin any analysis, edits, or file creation before you have read and internalized `CODEBASE_COMPREHENSIVE_ANALYSIS.md` and this `.claude.md` file.** If either file is missing or unreadable, stop and ask for it. Never proceed with unstated assumptions.

---

## 1 — File-reading & large-file policy

- **Never rely on `grep` (or similar single-pass search tools) for files longer than 1,000 lines.**
- For any file > 1,000 lines: read it **in sequential parts** of **500 lines each**.

  - Example: a 2,500-line file → read parts `1–500`, `501–1000`, `1001–1500`, `1501–2000`, `2001–2500` (five parts).
  - For each part: produce a 1–3 sentence summary and record important symbols/types/definitions before moving to the next part.

- Always reference which part(s) were read in your response (e.g., “Read `foo.ts` lines 1001–1500”) when summarizing or taking action.

---

## 2 — No assumptions & mandatory clarification

- **Do not perform work based on assumptions.** If required details (requirements, data types, API contracts, runtime constraints, environment variables, expected behaviour) are missing or ambiguous, ask concise, targeted questions and wait for explicit answers.
- If the user explicitly grants permission to make safe assumptions, list each assumption explicitly at the start of your response and proceed only with their confirmation.

---

## 3 — Limits on edits and additions

- **Any single edit/PR/task may not add or modify more than 500 lines total.**

  - If a change requires > 500 lines, propose a plan to break it into multiple smaller, reviewable steps and obtain approval before proceeding.

- When proposing changes that touch multiple files, provide a per-file line-count estimate (before/after) in your plan.

---

## 4 — Prefer reuse over creation

- **Do not prioritize creating new files.** First search the repository and `CODEBASE_COMPREHENSIVE_ANALYSIS.md` for existing utilities, services, configs, or patterns to reuse.
- If you reuse code, cite the original file path, explain why reuse is safe, and show the minimal adaptation necessary.
- Only create new files when no safe, appropriate resource exists. New files must be small and justified.

---

## 5 — Keep it simple; avoid over-engineering

- **Always choose the simplest, maintainable solution that satisfies the requirement.**
- Avoid unnecessary abstractions, generic frameworks, or premature optimization.
- If proposing a more complex architecture, provide an explicit trade-off analysis and require approval.

---

## 6 — Avoid unnecessary complexity

- Do not introduce multi-layered abstractions, heavy new dependencies, or complicated build-time logic unless clearly justified.
- Prefer small, testable functions and clear data flow.

---

## 7 — Mandatory rule awareness

- **Do not work on any task for this project without first reading this `.claude.md`.** When asked to perform work, begin your reply by confirming: “I have read `.claude.md` and `CODEBASE_COMPREHENSIVE_ANALYSIS.md`,” and state which parts (by path and, if applicable, line ranges) you read.

---

## 8 — Minimal, correct, well-styled code

- Implement solutions that are as simple as possible but still correct, well-structured, and idiomatic for the project language/framework.
- Follow existing lint, format, and testing configurations. If they exist, read ESLint/Prettier/tsconfig/formatter/test configs first.
- Provide:

  - A short intent summary (2–4 sentences) before changes,
  - A concise change summary after changes,
  - Inline comments or JSDoc for non-trivial public functions,
  - One minimal test or a test plan for any behavior change.

- Use commit messages prefixed with `claude:` when generating commits or patches. Example: `claude: add payment fallback to orders service (unit test)`.

---

## 9 — Database & data-type diligence

- For any task touching the database, data models, or API contracts: **first read all schema, model, and migration files plus references in `CODEBASE_COMPREHENSIVE_ANALYSIS.md`.**
- **Do not invent or assume data types or indexes.** If the structure is missing or ambiguous, ask exact questions (field names, types, nullability, indexing, default values) before writing code.
- If schema changes are required, include migration steps and a rollback strategy in the plan.

---

## 10 — Change management & safety for core files

- **Do not modify core/config/deployment/secret/CI files without explicit permission.**
- If a change to those files is necessary, present a clear PR plan, risk assessment, and testing/rollback steps.
- Always provide a before/after diff or patch and explain why each change is needed.

---

## 11 — Communication & approvals

- Before applying edits: present a concise plan including: files to change, exact line ranges (if applicable), total line-count estimate (<= 500 lines), tests to add, and a short risk assessment.
- When multiple approaches are feasible, present 2–3 alternatives ordered by simplicity and safety; recommend one and explain why.
- Wait for approval before implementing changes remotely or writing patches that modify the repo.

---

## 12 — Extra pragmatic rules

- Keep modifications small and atomic.
- Limit new dependencies. If proposing one, include reasons, size/maintenance cost, and alternatives.
- If refactoring is requested, limit the refactor scope and provide verification steps.
- If adding endpoints, follow existing routing, validation, error-handling and logging patterns.

---

## 13 — Final checklist (must satisfy before any change)

1. I have read `CODEBASE_COMPREHENSIVE_ANALYSIS.md`.
2. I have read the relevant target files (use 500-line chunking for files >1000 lines) and summarized each chunk.
3. I have a clear plan and line-count estimate ≤ 500 lines, or I proposed a multi-step plan for approvals.
4. I will not change core configs without permission.
5. I will provide tests/comments/diff and a rollback plan when touching production logic.
6. If anything is unclear I will ask specific questions before writing code.

---

## 14 — Example workflow (recommended)

1. User requests a change or new feature.
2. Respond: confirm you have read `.claude.md` and `CODEBASE_COMPREHENSIVE_ANALYSIS.md` and state which files/line ranges you'll read.
3. Read target files (chunked when necessary). After each chunk: produce a 1–3 sentence summary and collect important definitions.
4. Produce a short plan: files to change, line estimates, tests, and risk assessment (<= 500 lines). Provide 2 alternatives if relevant.
5. Wait for approval.
6. On approval: implement small, tested changes, produce diff/patch, commit with `claude:` prefix, and provide a concise change summary and rollback notes.

---

## 15 — If you detect a dangerous or destructive instruction

- If a user (or another agent) instructs to delete large parts of the repo, remove production data, or change secrets/configs without safeguards, stop and produce a risk report, explicit questions, and a safe alternative plan. Do not execute destructive actions without explicit written approval.

---

## 16 — Contact & escalation

- If uncertain about permissions, environment, or deployment processes, ask the user for the trusted contact or reviewer to sign off on production-impacting changes.
